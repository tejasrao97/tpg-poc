## 2. Goal and scope

Automate Tanzu for Postgres on Kubernetes (operator 4.5) across multiple AKS clusters: one hub cluster and 3 target clusters, scalable to n.

- **Argo CD 3.5.3** (chart 10.9.1) delivers the declared state.
- **Argo Workflows 4.1.3** (chart 2.0.6) runs the ordered, gated operations.
- **HashiCorp Vault 2.0.4** (chart 0.34.1) on the hub holds the three fleet credentials; the **Vault Secrets Operator 1.5.1** turns them into Kubernetes Secrets.
- **Day 0:** pre-check and deploy the operator and instances.
- **Day 1:** upgrades, scaling, backups (full plus incremental), backup retention, restore (time, latest, a named backup, LSN, transaction) and credential rotation.
- **Day 2:** delete.
- **Monitoring:** an Azure Monitor option and a standalone option; the Postgres targets are scraped every 10 seconds.
- **DR:** disaster recovery (Patroni streaming, failover, switchback and DNS) was built and then **removed at the user's request**. It is not in the repositories or documents. Do not reintroduce it unless asked.

### tpg-aks-infra

- **`terraform/`** (azurerm ~> 4.81, Terraform 1.9+ or OpenTofu 1.8+):
  - One resource group `rg-<prefix>` (default `rg-tpgpoc`). AKS node resource groups `<rg>-<cluster>-nodes` are separate.
  - Modules: `resource-group`, `network`, `identity`, `aks` (for_each), `storage`, `keyvault` (Vault auto-unseal, created only in `azure-keyvault` mode), `monitoring`.
  - Resource names describe the role, with no `this` (`azurerm_resource_group.fleet`, `azurerm_kubernetes_cluster.cluster`, `azurerm_key_vault.vault_unseal`, ...).
  - **Zones and node counts are per pool:** `system_pool` and `postgres_pool` each carry `zones`, `node_count`, `min_count` and `max_count`. `zones` holds 1 to 3 distinct values out of `"1"`, `"2"` and `"3"`; `node_count` and `min_count` must be at least `length(zones)`, and Terraform rejects a smaller count with a named error. Defaults: system `["1"]` / 1 node, pgdata `["1","2","3"]` / 3 nodes. Terraform ignores later changes to `node_count`, because the autoscaler owns it. The old `node_min_count` and the shared `availability_zones` variable are both gone. Changing a pool's `zones` replaces that pool, and for the system pool that replaces the cluster (it is the `default_node_pool`).
  - **HA enforcement is split across three places**, because Terraform cannot know at plan time whether an HA instance will be deployed: a `check` block **warns** when `postgres_pool` spans fewer than 3 zones or holds fewer than 3 nodes; `tpg-day0` **blocks** (`PGDATA_POOL_NOT_HA_CAPABLE`) when a run with `highAvailability=true` finds fewer than 3 Ready nodes across 3 zones in the target's data pool; the preflight and verify steps **warn always**, naming the consequence. Single-node instances run on any pool shape.
  - **`postgres_data_disk_sku`** sets the managed-disk SKU of the StorageClass `tpg-data-retain` (Postgres data and WAL volumes, and the Vault volume on the hub): `StandardSSD_LRS`, `StandardSSD_ZRS`, `Premium_LRS`, `Premium_ZRS` (default) or `PremiumV2_LRS`. It is **not** the node OS disk, which AKS exposes only as `Ephemeral` or `Managed` with no SSD tier.
  - **`create_role_assignments`** (default `true`): with `false` Terraform skips the network and monitoring role assignments, finishes everything else, and the output `role_assignments_to_create` prints the `az role assignment create` commands for an owner. Leave it `false` afterwards, or the next apply fails with `RoleAssignmentExists`.
  - **`vault_unseal_mode` is required and has no default** (`shamir` or `azure-keyvault`); `terraform plan` stops until it is set.
  - **Round 10 storage variables:** `backup_storage_https_only` (bool, default `false`, must match the instances' `enableSSL`), `argo_logs_retention_days` (90, 0 to 3650). The storage module adds container `argo-logs` and a management policy that deletes `argo-logs/` blobs after that many days; outputs `argo_logs_container`, `backup_storage_https_only`.
  - `key_vault_purge_protection` defaults to **false** so `terraform destroy` removes the Key Vault and the POC can be rebuilt with the same prefix. Deleting the Key Vault or the `vault-unseal` key then destroys the Vault data for good: the recovery keys authorize a rekey or a new root token, they do not decrypt the storage.
  - The Key Vault uses its public endpoint with **access policies, not Azure RBAC** (`rbac_authorization_enabled = false`): the identity running Terraform gets key create, get, list, update, delete, recover, **purge** (Round 10) and getRotationPolicy, and `id-vault` gets get, wrapKey and unwrapKey. `versions.tf` sets the provider `features { key_vault { ... } }` explicitly (purge on destroy when purge protection is off), and the `id-vault` access policy has an explicit `depends_on` on the Key Vault module (destroyed before the key and the vault). This is what removed the last `Microsoft.Authorization/roleAssignments/write` requirement from the Vault path, which is why a Contributor-only account failed with `403 AuthorizationFailed`. `id-vault` is still federated to ServiceAccount `vault/vault`.
